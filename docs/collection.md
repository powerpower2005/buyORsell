# 수집 v2.0.0 · SOXX 데이터 복구 v1.0.0

2026-11-16. 수집·복구 버전은 [설정](../config/collection-versions.json)에 기록합니다. 지표 수식·시그널 조건·성과 계산 엔진은 바꾸지 않았으므로 기존 분석 항목별 버전은 유지합니다.

## 발견한 원인

SOXX 일봉의 잘못된 15개 행은 삼성전기 `009150:KRX`의 같은 날짜 **시가·고가·저가·종가·거래량 전체**와 일치합니다. 예를 들어 2026-06-19 SOXX로 저장된 종가 2,270,000과 거래량 1,728,303은 삼성전기 행과 동일합니다. 해당 날짜들은 미국 증시 휴장일입니다. 단순 소수점 오류나 SOXX의 실제 급등이 아닙니다.

기존 `fetchBarsGoogleFinance`는 모든 종목·백필 요청에 `BarsFetch-v1!Z1`을 재사용했습니다. 요청 A가 수식을 넣고 기다리는 동안 요청 B가 덮어쓰면 A도 B의 OHLCV를 읽을 수 있습니다. 파서는 숫자 행이 있으면 성공으로 처리했고, 요청 종목·날짜 범위나 계산 소유권을 검증하지 않았습니다. 워크플로 동시성 그룹도 종목·이슈별로 달라 같은 계산 셀을 보호하지 못했습니다. 같은 스프레드시트를 쓰는 다른 저장소와도 충돌할 수 있습니다.

정상 SOXX 데이터를 이후에 받아도 `mergeOhlcv`는 날짜를 추가·덮어쓰기만 합니다. 미국 휴장일은 정상 응답에 없으므로 그 날짜에 잘못 들어간 한국 종목 행이 계속 남습니다. 이 두 단계의 결합을 회귀 테스트로 재현했습니다. 오염 출처와 현재 코드의 실패 경로는 확인했지만, 최초 오염 당시 개별 요청의 실행 순서까지 남아 있는 것은 아닙니다.

전체 기간을 실제 재조회하자 **분할 보정 기준의 혼합**도 발견했습니다. SOXX는 [iShares의 SEC 공시](https://www.sec.gov/Archives/edgar/data/1100663/000119312526361162/d133118d497.htm)에 따라 2026-11-05부터 3:1 분할 기준으로 거래됐습니다. 기존 갱신은 최근 730일에만 적용되고 900봉 이상이면 과거 백필도 건너뛰어, 2024-11-08 이전의 오래된 가격은 새 보정 기준으로 갱신되지 않았습니다. 예를 들어 저장된 2024-11-08 종가 231.36은 재조회에서 77.12였고, 다음 저장 거래일인 11-11은 이미 75.19여서 과거 차트에 인위적인 단절이 생겼습니다.

실제 공급자 대조에서 480개 일봉 가격이 달랐습니다. 478개는 약 3배 차이였고, 2024-10-15와 2024-11-05의 두 행은 그 비율만으로 설명할 수 없는 추가 차이가 있었습니다. 10-15 거래량도 73,112 → 6,421,198로 달랐습니다. 두 행의 최초 오류 원인은 단정하지 않고, 정확한 이전·재조회 값을 별도 검토해 복구 근거에 남겼습니다.

전 종목 간 동일 OHLCV 비교에서는 이미 추적 제외 중인 `CRD:NTYSE`에서도 `000660:KRX`와 일치하는 이력이 발견됐습니다. CRD는 종목 코드 자체 확인이 필요하므로 이번 SOXX 복구에 섞어 수정하거나 추적 대상으로 복귀시키지 않습니다.

## 기존 데이터 복구

원본 커밋 `8e19ef6f682218312637b911259f0a0aa30f2966`에서 다음 조건을 동시에 만족하는 15개 일봉만 제거했습니다.

1. 삼성전기 행과 날짜·OHLCV 모두 정확히 일치.
2. 확인된 미국 휴장일 목록에 포함.
3. 사전에 검토한 15개 날짜 집합과 정확히 일치. 증거가 달라지면 복구 스크립트가 중단.

1차로 일봉 999 → **984개**로 정리하면서 나머지 가격·거래량과 기존 `fetchedAt`을 유지했습니다. 그 후 2022-12-12~2026-11-12 전체 기간을 새 격리 시트에서 실제 재조회한 결과로 480개 일봉 가격과 거래량 1건을 바로잡았습니다. 로컬에서 일괄 3으로 나누거나 거래량을 곱하지 않고 공급자가 반환한 정확한 값을 사용했습니다. 날짜 집합은 그대로 984개이며 휴장일 봉을 새로 만들지 않았습니다.

최종 일봉에서 주봉 200개와 월봉 48개를 다시 만들었고, 원본 커밋 대비 **109개 주봉·36개 월봉**이 정정됐습니다. 최종 `fetchedAt`은 실제 공급자 재조회 시각입니다. 로컬 제거 시각은 `data_recovery.repaired_at`, 공급자 대조 반영은 `provider_reconciled_at`으로 구분합니다. 원본·두 복구 단계의 해시, 제거한 15행, 정정한 480행의 전후 값, 실제 실행 링크와 근거는 [감사 기록](../data-repairs/2026-11-16.json)에 있습니다.

## 검증·운영

```powershell
npm run test:collection
npm run test:stale-refresh
npm run validate-data
# 이미 적용된 동일 복구는 아무것도 변경하지 않음
node scripts/repair-soxx-history.mjs
```

CI `Collection integrity`는 요청 경쟁 재현·격리·실패 정리·범위/가격 검사·근거가 바뀐 복구 차단·실제 SOXX 집계 일치를 검사합니다.

보관 기간은 `sheetsLookbackDays`를 넘겨 확장하지 않습니다. 최초 수집과 백필 정책은 유지하되 기존 종목의 실제 갱신은 `historyRefreshOptions`로 전체 보관 기간을 요청합니다. 제공자가 이전 날짜 일부를 누락하면 기존 가격과 다른 보정 기준이 조용히 섞이지 않도록 실패합니다. 단순히 신선도 검사로 건너뛴 실행은 공급자 재조회가 아닙니다.

Actions **Fetch Quote**의 `verify_soxx_recovery=true`, ticker=`SOXX:NASDAQ`는 기존 기간 전체를 `NASDAQ:SOXX`로 새 격리 요청하여 복구 결과와 대조합니다. `data/`나 GitHub 브랜치는 변경하지 않으며, 출처·기간·개수·해시·차이 날짜만 담은 검증 보고서와 공급자 quote를 artifact로 남깁니다. 불일치 시 실패하며 추적 복귀 전에 검토해야 합니다. 자격증명은 기존 Actions Secrets를 사용합니다.

2026-11-16 검증 결과: 수집·복구 테스트 12개와 전체 데이터 스키마 검사가 통과했습니다. [별도의 두 번째 공급자 요청](https://github.com/powerpower2005/buyORsell/actions/runs/43733462054)에서 984개 날짜·OHLCV가 모두 일치했고, SHA-256도 동일했습니다. 영구 보관한 [검증 보고서](../data-repairs/2026-11-16.provider-verification.json)에서 확인할 수 있습니다. 기존 stocker 추적식의 Wilder ATR(14)은 476.8299 → 8.3966으로 바뀌었습니다. 이는 데이터 정정 결과이며 추적 배수를 조정한 결과가 아닙니다.

일반 병합을 무조건 전체 교체로 바꾸지는 않았습니다. 제공자가 일부 자료만 반환하는 상황에서 정상 과거 이력을 삭제할 수 있기 때문입니다. 복구는 증거를 가진 별도 절차로 수행합니다.

## 정기 배치 전체 누락 검사 — collection-v3.2.0

한국시간 월~금 **11:00·18:00·23:00**과 토요일 **09:20**에 배치를 예약합니다. 토요일 수집은 미국 금요일 장의 일봉 확정 기준인 토요일 09:00 KST 이후에 시작합니다. stocker의 토요일 12:25·19:25 평가가 게시된 일봉을 읽습니다. 배치마다 최신 봉이 신선한 종목도 검사합니다. 활성 종목을 일봉 단위로 한 번씩 묶어 전체 보관 기간(현재 1,500일 및 이미 보관 중인 날짜)을 강제 조회하고, Google→독립 Yahoo→필요 시 국내 Naver 검증을 통과한 봉을 병합합니다. 중간 거래일 누락과 보관 기간 앞부분의 부족분을 보충하고 주봉·월봉을 재생성합니다. 실제 휴장·거래정지일은 빈 봉으로 만들지 않습니다.

일봉 파일 자체가 없으면 같은 종목의 Git 커밋 원본에서 복구 ID 등 메타데이터를 읽고 다시 공급자 검증을 거쳐 복원합니다. 복원할 커밋 근거가 없으면 실패합니다. 주봉·월봉 파일 누락도 일봉에서 재생성합니다. 격리 종목은 계속 제외합니다.

보고서에 종목별 과거 날짜 보충(앞부분 확장 포함), 새 거래일, 기존 봉 정정, 복구 파일, 실패 사유를 남깁니다. 공급자에만 누락된 날짜는 가격을 추정해 채우지 않고 오류로 보고합니다. **한 종목이라도 검사에 실패하면 전체 배치를 실패시키고 데이터 커밋을 건너뛰어 기존 원격 데이터를 유지합니다.** 검사는 끝까지 진행하므로 여러 종목의 문제를 한 보고서에서 볼 수 있습니다. 최종 데이터·집계·인덱스 검증 및 원격 병합 후 재검증도 유지합니다. 데이터 변경 작업은 같은 Actions concurrency 그룹에서 직렬 실행합니다.

`batch_audit` 2.0.1부터 GOOGLEFINANCE 표가 비어 있거나 독립 가격 비교가 불일치하면 해당 종목의 전체 기간을 새 임시 시트에서 다시 요청합니다. 최초 요청을 포함해 최대 세 번이며, 매번 같은 검증을 전부 통과해야 저장할 수 있습니다. 연속 실패 시 배치 전체의 데이터 커밋을 건너뜁니다.

수동으로 같은 배치를 실행하려면 Fetch Quote에서 ticker=`ALL`, `batch_refresh=true`를 선택합니다. `audit_universe` 및 `verify_soxx_recovery`는 false로 둡니다. 기존 읽기 전용 감사와 구분되는 실제 수집·복구·커밋 경로입니다. 보고서는 `fetch-run-report` artifact와 Actions Summary에 기록됩니다.

### 예약 수집 실패 복구

`main`의 예약 **Fetch Quote** 첫 실행이 실패하거나 시간 초과되면 **Recover quote collection**이 동일한 전체 이력 수집 작업을 한 번 실행합니다. 실행 제목에 원래 실패한 실행 번호가 표시됩니다. 복구는 수집과 같은 동시성 그룹에서 직렬화되며 공급사 대조와 최종 데이터 검사를 통과한 전체 배치만 게시합니다.

토요일 09:20 수집부터 12:25 평가까지 예정 간격은 3시간 5분입니다. 수집과 자동 복구의 작업 제한은 각각 45분이며 Actions 시작 시간과 공급사 게시 시간은 달라질 수 있습니다. 12:25 평가가 먼저 시작하면 19:25 평가에서 최신 게시본을 다시 읽습니다. 예약 실행 자체가 누락됐거나 성공 결과에 예상 거래일 일봉이 없으면 해당 시장의 휴장을 확인한 뒤 수동 복구를 판단합니다. [stocker 일정과 실패 대응 명세](https://github.com/powerpower2005/stocker/blob/main/docs/specs/chart-signal.md#실행-일정과-실패-대응).

1. stocker의 종목 시그널 오류에 `Stale quote`가 있으면 buyORsell Actions에서 **Fetch Quote** 실패와 이어지는 **Recover quote collection**의 결과를 확인합니다.
2. 복구도 실패하면 해당 실행의 `fetch-run-report`에서 실패 종목과 사유를 확인합니다. 같은 과거 봉에서 반복 실패하면 격리된 공급사 응답을 저장본 및 독립 가격과 대조합니다. 표본이 일치할 때에만 정확한 제공사 정정을 기록하고, `main`에서 **Recover quote collection → Run workflow**로 수동 복구합니다.
3. 복구 실행에서 모든 활성 종목이 통과하고 데이터 커밋이 반영되면 stocker **Chart signal alerts**의 `dry-run`으로 갱신 데이터와 기존 추적 상태를 검증합니다.

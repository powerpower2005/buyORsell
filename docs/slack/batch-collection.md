# 종목 데이터 배치 결과 — 알림 v1.0.0

출시 묶음: `collection-v3.3.0` (2026-11-16). [가이드 목차](README.md) · [수집 운영](../collection.md) · [모듈 버전](../../config/collection-versions.json).

## 발송 범위와 채널

buyORsell의 `Fetch Quote` 평일 정기 배치와 `workflow_dispatch`의 `batch_refresh=true` 실행 결과를 보냅니다. 단일 종목 수동 수집·이슈 요청, 읽기 전용 감사, SOXX 검증은 이 알림 대상이 아닙니다.

| 결과 | 채널 | 조건 |
| --- | --- | --- |
| 검사·저장 성공 | `SLACK_LOG_CHANNEL_ID` | 활성 종목 전체 검사, 보고서 보관·읽기, 최종 데이터 검증, GitHub 저장 단계가 모두 성공 |
| 수집·누락 검사·검증·저장 실패 | `SLACK_ERROR_CHANNEL_ID` | 실패 단계와 안전한 원인을 표시. 보고서가 없으면 확인 가능한 실행 정보만 표시 |
| 성공 로그 전송 확인 실패 | `SLACK_ERROR_CHANNEL_ID` | 성공 채널로 재전송하지 않고 별도 전송 실패를 1회 통보; Actions도 실패 |

시그널·섹터 채널 설정을 읽거나 대체 대상으로 사용하지 않습니다. 로그/오류 채널은 서로 달라야 합니다. 변경 없는 정상 배치도 전체 재검사와 저장 단계 확인이 끝나면 성공 로그를 보냅니다. 여러 종목 중 하나라도 검사 실패하면 해당 배치 데이터 저장을 건너뜁니다.

## 메시지 내용

성공에는 검사/통과/격리 제외 수, 과거 날짜 보충·신규 봉·기존 봉 변경·파일 복구 수, 종목별 기준 거래일, 한국시간 완료 확인 시각, 실제 출처 태그, 저장 커밋과 Actions 실행 링크를 넣습니다. **과거 날짜 보충에는 보관 기간 앞부분 확장도 포함**하므로 모두 오류로 누락된 봉이라고 부르지 않습니다. 상세 종목은 최대 12개, 나머지는 Actions의 `fetch-run-report` artifact에서 확인합니다.

실패에는 한국시간 감지 시각, 실패 단계, 원인 분류, 종목별 기준 거래일과 기록된 감지 시각, 실행 링크를 넣습니다. 종목 검사 실패의 기준일은 검사 전 보관 데이터의 마지막 거래일입니다. 실행 준비 단계에서 실패해 시장 날짜를 알 수 없으면 `확인 불가`로 표시하며 실행일을 거래일로 대신 쓰지 않습니다. 원본 공급자/Slack 오류 응답, 토큰, 인증 자료는 메시지에 넣지 않습니다.

예시 (수치는 설명용):

```text

기준일(거래일): 2026-11-13
```

## 설정과 실행

**buyORsell 저장소**의 Settings → Secrets and variables → Actions → Repository secrets에 다음을 설정합니다. stocker의 Repository Secret은 자동 공유되지 않습니다.

- `SLACK_BOT_TOKEN`: 기존 Slack 봇 토큰 (`chat:write` 권한).
- `SLACK_LOG_CHANNEL_ID`: 기존 수집 성공 로그 채널 ID.
- `SLACK_ERROR_CHANNEL_ID`: 기존 작업 실패 채널 ID.

해당 봇이 두 채널에 게시할 수 있어야 합니다. 채널 이름 대신 ID를 사용합니다. 시그널 채널을 위 두 값에 지정하지 않습니다. 오류 채널이나 토큰이 없으면 Slack으로 오류를 보낼 수 없으므로 Actions의 알림 단계가 실패합니다. 로그 설정만 잘못됐고 오류 채널이 유효하면 오류 채널로 설정 오류를 알립니다.

배치 완료 후 별도 `notify-batch` 작업에서 원래 실행 커밋의 알림 코드를 읽습니다. 수집 작업의 설치·준비 실패도 처리할 수 있도록 알림 작업은 npm 설치가 필요 없습니다. `fetch-run-report`가 없어도 오류를 구성합니다. 최종 저장 함수는 원격 변경을 병합한 뒤에도 데이터를 재검증합니다. GitHub 저장 실패·시간 초과는 원격 반영 여부가 불명확할 수 있어 `저장 완료를 확인하지 못함`으로 표현합니다.

[Slack chat.postMessage](https://docs.slack.dev/reference/methods/chat.postMessage/) 응답의 `ok`, 대상 채널, 메시지 `ts`가 모두 확인돼야 전송 성공으로 처리합니다. 확인된 메시지는 `batch-notification-receipt` artifact에 알림 버전·종류·채널·ts를 남깁니다. 토큰은 저장하지 않습니다. 실패한 성공 로그를 대신 알린 오류 메시지는 Actions 로그로 결과를 확인합니다.

한 실행 시도에서 기본 결과 메시지는 한 번만 POST합니다. 시간 초과 후 중복을 피하려고 자동 재시도하지 않습니다. Slack이 수신했지만 응답이 유실될 수 있으므로 정확히 한 번 전달을 보장하지는 않습니다. 수동으로 작업을 재실행하면 새로운 실행 시도의 알림이 발송됩니다. Actions 자체 장애·전체 강제 취소나 알림 작업 자체의 실행 준비 실패는 Slack 도달을 보장할 수 없습니다. 오류 채널 전송까지 실패하면 Actions 실패로 남고 다른 채널로 우회하지 않습니다.

## 이전 버전과 검증

| 항목 | collection-v3.2.0 | collection-v3.3.0 |
| --- | --- | --- |
| 배치 결과 | Actions 요약·artifact | 기존 보고서 + 성공/오류 Slack 분리 |
| 성공 조건 | 검사 후 검증·커밋 | 기존 조건 유지, Slack에는 저장 성공까지 확인한 뒤 표시 |
| 배치 보고서 | `batch_audit` 2.0.0 | 2.1.0: 기준일·실패 감지·완료 시각 추가 |
| Slack 알림 | 없음 | `batch_notification` 1.0.0 신규 |
| 지표·시그널·추적식 | 기존 버전 | 변경 없음 |

`npm run test:collection`에서 채널 분리, 모든 단계 실패, 보고서 누락/불일치, 한국시간 변환, 원본 오류 비노출, 불명확한 POST 재시도 금지, Slack 응답 확인, 설정 누락, 메시지 길이를 검증합니다. 기존 전체 수집·복구 회귀 검사와 데이터 검증도 유지합니다.

로컬 검증: 수집·복구·알림 회귀 **35개**, 주말 신선도 검사, **20종목·60개 데이터 파일**의 유효성·집계·인덱스 검사가 통과했습니다. 오류 알림 경로는 모의 Slack 응답으로 검증하며 실제 발송 여부와 구분합니다.
